## 2. 分层与依赖方向

**现状**（两层，页面直接持有 mock 数据）：

```
main.dart → routes/index.dart → pages/main/index.dart
                                    ├─ pages/todo/index.dart ─┬─ widgets/todo_card.dart → components/todo_tag.dart
                                    │   (硬编码 List<Todo>)    ├─ widgets/today_progress.dart
                                    │                         └─ widgets/section_header.dart
                                    ├─ pages/period/index.dart      (占位)
                                    ├─ pages/schedule/index.dart    (占位)
                                    └─ pages/statistics/index.dart  (占位)
                                          models/todo.dart ← 被 todo 页与卡片共同引用
```

**当前分层**（已落地，依赖方向单向向下）：

```
main.dart (ProviderScope)
  → routes/index.dart (onGenerateRoute)
      → pages/main/index.dart (IndexedStack + 启动引导 + 跨日校准)
          ├─ pages/todo/    index.dart · edit/ · widgets/
          └─ pages/period/  index.dart · edit/ · detail/ · item_edit/ · widgets/
                ↑ 只渲染与派发意图，不写业务规则、不 import db_helper
          logic/     todo_actions · periodic_actions · app_actions
                ↑ 写操作编排：调 Repository → 按失效矩阵 invalidate → UI 反馈
          stores/    db_providers · todo_store · periodic_store · invalidation · bootstrap
                ↑ Riverpod，只调用 repositories，不写 SQL
          repositories/  task · periodic · periodic_item · generator · completion · cycle_counter · skips
                ↑ SQL 唯一出现处
          utils/db_helper.dart  sqflite 单例 · PRAGMA foreign_keys=ON · kSchema DDL
          models/    todo · periodic · periodic_item · cycle_rule · todo_groups · 两个枚举
          components/  跨页复用 UI（标签、左滑动作、表单、选择器、空/错态）
```

**约定（已在代码中执行）**：SQL 只在 `repositories/`；`pages/` 不 import `db_helper`；
写操作后一律调用 `stores/invalidation.dart` 的三个封装函数，**禁止零散手写 `invalidate`**；
周期日期算术集中在 `models/cycle_rule.dart` 与 `utils/date_util.dart`，**不使用** SQLite 的
`date(x,'+N month')`（月末溢出为进位而非收敛，实测 `2026-01-31 +1 month = 2026-03-03`）。

### 7.2 实施期新发现（已修）

| 编号 | 问题 | 影响 | 处理 |
| :-- | :-- | :-- | :-- |
| **N1** | 硬删除与生成引擎幂等键冲突：实例被删后 `UNIQUE(periodic_item_id, cycle_index)` 空出，下一次窗口生成会把它**原样写回** | 用户删掉的待办在重启 / 跨日 / 新建周期项后自己复活，属于数据正确性缺陷 | 新增 `periodic_skips` 墓碑表（schema v2.2 / docs/02 §4.4），生成时跳过，撤销删除时清除；3 个回归用例 |
| **N2** | 「完成一轮 → 生成下一轮」若沿用 30 天窗口，长周期（如每 40 天）永远等不到下一轮 | TC-08 不成立 | 拆出 `generateCycle(periodicId, k)`：不受窗口限制，但仍遵守 `is_active` / `end_date`，且不补生成已过去的轮次 |
| **N3** | `databaseFactoryFfi` 把库跑在独立 isolate，其完成事件不是 microtask | `testWidgets` 的 fake-async 环境里页面永远停在 loading，`pumpAndSettle` 挂死（实测单测超 4 分钟不返回） | Widget 测试统一用 `databaseFactoryFfiNoIsolate`（`TestStore.create(noIsolate: true)`），并给 `pumpAndSettle` 加 10 秒短超时 |
| **N4** | `SwipeAction` 的 `AnimationController` 用 `late final` 懒初始化 | 未滑动过的卡片被销毁时，首次访问发生在 `dispose()`，element 已 deactivated → 抛「Looking up a deactivated widget's ancestor is unsafe」 | 改为在 `initState` 中立即创建；由 Widget 测试捕获 |
| **N5** | `IndexedStack` 同时持有待办页与周期页，两个 `CupertinoSliverNavigationBar` 使用同一默认 Hero tag | 路由切换时抛「multiple heroes that share the same tag within a subtree」 | 各页显式指定唯一 `heroTag`（`todo-large-title` / `periodic-large-title`）；由 Widget 测试捕获 |
| **N9** | 列表左滑删除手势的右滑方向无任何行为，用户反馈「右滑并不清楚」，手势语义不完整 | 2026-10-05 按用户决策**整体移除滑动手势**（待办卡 / 日程卡 / 周期卡 / 周期项行），删除统一走编辑页红色按钮（待办、周期、周期项均有），保留二次确认 + 5 秒撤销 + 三级删除语义；`SwipeAction` 组件与其测试一并删除 | 
| N6 | 无 CI | 回归全靠本地 `flutter analyze` + `flutter test` | 建议后续加 GitHub Actions（`analyze` + `test`，无需真机） |
| N7 | `completed_count` 为绝对重算，删除已完成实例会让它回退 | 与「已完成轮数」的直觉略有出入 | 与 Q5「删除同时从分子分母消失」一致，属预期行为；已在 `CycleCounter` 注释与 docs/02 §6.3 #22 记录 |

### 7.3 遗留注意事项

| 项 | 说明 |
| :-- | :-- |
| **Q8 的可感知后果** | 修改周期规则后，因为已预生成未来 30 天，「新规则」实际要等这批轮次消耗完才可见（编辑页已明示文案）。若产品希望「立即按新规则重排未来待办」，需要新增一个显式动作：删除未来未完成实例（清墓碑）后重新生成 |
| 生成窗口常量 | `PeriodicGenerator.kWindowDays = 30`、`kMaxCyclesPerRun = 2000`（防死循环）；调整时同步更新 docs/02 §7.4 |
| 墓碑表增长 | 依赖 `ON DELETE CASCADE` 随周期项回收；长期使用的孤儿墓碑（周期项仍在但实例早删）量级极小 |
| **N13** | 前台兜底的「到期前 90s 抢走 OS 排期」会让前台提醒变不准：收走系统闹钟后改由 15s 轮询补发，熄屏/ROM 冻结计时器时还会拖尾，且引入双发风险 | 重构为**OS 主通道 + 巡检只修丢单**：到期前一律不碰排期；到期后 60s 宽限内等 OS；超宽限且排期仍在才判定被 ROM 丢弃并补发收回；排期消失但本进程排期成功过（`_armedIds`）= OS 已送达，静默去重；从未排期成功 = 排期异常，前台补发。恢复与 Phase 6 初版同等的到点准确性 |
| **N12** | N11 的前台兜底**自身有两个缺陷**（一加 13 复测仍不响 + 横幅不出现） | ① `computeForegroundPlan` 把「到期 + 不在 pending + 未发过」误判为后台已送达：而 pending 为空恰恰是 90s 前置接管自己 cancel 的结果 → 巡检趟永远不进 toShow；② 横幅依赖 `canScheduleExactNotifications()`，该查询在部分机型返回 null 被 `?? true` 兜成已授权，而排期抛的 `exact_alarms_not_permitted` 才是硬证据 | ① 拆出 `seeding` 参数：播种趟才标记 assumeDelivered，巡检趟到期未发一律补发（回归用例锁定）；② 排期捕获到 exact_alarms_not_permitted 时置 `_exactAlarmDenied`，checkHealth 以其为准 |
| **N11** | 一加 13（ColorOS / Android 17）实测：精确闹钟被拒降级为非精确后，**App 存活期间到点也不响** —— 国产 ROM 对非精确闹钟的延迟/丢弃不受 Doze 白名单保护 | 新增**前台兜底巡检**（15s 一次）：距到期 ≤90s 的任务收回 OS 排期改由 App 自己到点发；已到期 ≤5min 且 OS 排期仍在（= 闹钟被丢弃）立即补发；启动/回前台时把「已到期且 OS 排期消失」的任务播种为已送达防双发；进后台停止巡检并 `reconcile()` 把提醒交还 OS。决策逻辑为纯函数 `computeForegroundPlan`，6 个单测覆盖 |
| **N10** | 「杀掉 App 后到点收不到通知」的三个真实根因 | ① Android 12+/14+ 未授「精确闹钟」时 `exactAllowWhileIdle` 抛异常，且旧实现**一条异常中断整批排期** → 杀进程后系统里根本没有排期；② 国产 ROM 把「划掉应用」实现为强制停止，系统会取消该包全部闹钟，属系统行为，代码无法绕过；③ iOS/macOS 通知权限被拒时静默丢弃 | ① 排期改为**逐条隔离失败** + 精确→非精确自动降级（延迟几分钟但不丢）；②③ 新增**通知自检横幅**：待办页首屏检测系统通知开关与精确闹钟授权，被拒时给出原因 + 「去开启」一键跳转系统设置（自研 `qingyun_todo/system` 通道，Android/iOS/macOS 三端各 10 行原生代码）；国产 ROM 自启动需用户在系统设置中开启，横幅文案已说明 |
| 通知的平台差异 | Android 14+ 的精确闹钟需用户单独授权（未授权时 `exactAllowWhileIdle` 会降级或抛错，reconcile 已 try/catch 兜底）；iOS 焦点模式下 `timeSensitive` 才能穿透；macOS 仅开发态验证。真机表现需用户在 Android / iOS 实机确认 |
| tyme 假日数据时效 | 内置法定假日/调休数据覆盖至 **2026-10-10**；国务院公布新一年安排后需升级 tyme 版本，否则该年不显示班/休角标（农历/节气不受影响）。`LunarUtil` 有 4000 条结果缓存 |
| Widget 测试的 finder 稳定性 | 每日周期会在多个分组生成同名实例，断言需用 `findsWidgets`；`IndexedStack` 下切 Tab 建议用 `find.text('周期').last` |
