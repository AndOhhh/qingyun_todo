# 青云待办 · 文档中心

> **青云待办（`qingyun_todo`）**：Flutter + SQLite 的单机版待办 App，iOS 风格 UI，无账号体系、无服务端。
> 核心特色是**自定义天数周期**——一个周期可以有 N 天，且每一天能安排不同的事项。

**文档基线**：基于提交 `9c74fe6` 与 `lib/` 实际代码（56 个 Dart 文件 / 8535 行）+ `test/`（75 个用例）逐项核对；schema 与需求已并入 **2026-09-25 功能评审决策**（见下方 Q 表）与**实施期修订**（schema v2.2，见下方 Q15 / 02 §6.3）。
**实施进度**：待办页 + 周期模块（Phase 1~3）已全部落地，mock 数据清零；日程页 / 统计页 / 提醒通知仍为占位。
原 `PROJECT_SUMMARY.md`、`tables.md`、原始需求 `.ini` 已重构进下列文档并删除，如需查阅旧版可从提交 `4d301a0` 找回。

| 项 | 约定 | 示例 |
| :-- | :-- | :-- |
| 日期 | `YYYY-MM-DD`（本地时区） | `2026-09-25` |
| 时间 | `HH:mm`（24 小时制） | `09:30` |
| 时间戳 | `YYYY-MM-DD HH:mm:ss` | `2026-09-25 09:30:00` |
| 布尔 | `INTEGER` `0`/`1`（DB）、`bool`（Dart） | `1` |
| 颜色 | `#RRGGBB` | `#007AFF` |
| 枚举 | DB 存枚举 `name`；优先级小写、周期类型大写 | `high` / `MONTH` |
| 天序 `day_offset` | **0-based**，`0` = 周期第 1 天 | — |
| 轮次 `cycle_index` | **0-based**，`0` = 第 1 轮；来源周期删除后仍保留 | — |
| 术语 | 统一用"常规待办"（不用"日常"）、"周期项"（模板）、"周期实例"（生成的记录）、"孤儿记录"（来源周期已删的已完成实例） | — |
| 文档元信息 | 写"基于提交 `<短 hash>` 核对"，不写无法验证的手工日期 | — |

## 待确认问题清单

> 文档中带 🔶 或 **Qn** 标记处均指向本表。**✅ = 已定案（2026-09-25 功能评审）**；未标 ✅ 者仍待定，按"建议默认"执行。

### 已定案

| 编号 | 问题 | 结论 | 影响范围 |
| :-- | :-- | :-- | :-- |
| **Q1** ✅ | 周期是否需要"暂停 / 终止日期"？是否补生成历史实例？ | 采纳默认：需要 `is_active` 暂停与 `end_date` 终止；**不补生成历史**，从当前轮开始 | 02 §4.1、04 §5、Phase 3 |
| **Q2** ✅ | 子任务是否纳入 v1？ | **移除子任务功能**——每条待办都是独立任务。`subtasks` 表不建（DDL 移入 [02 附录](./02-数据库设计.md)），并清理 `Todo.subDone/subTotal`、卡片 `x/y` 标签与 mock 数据 | 02 §4.4、03 R11、Phase 2 |
| **Q5** ✅ | 待办删除语义 | **硬删除**，但必须与"完成"严格区分（手势方向、颜色、文案、确认强度、统计口径全不同）+ 5 秒撤销；**删除周期时保留已完成的周期任务记录**（未完成实例物理删除，已完成实例断开关联后保留为历史；手动删除的实例不保留） | 02 §7.3、04 §4.1、Phase 2/3 |
| **Q4** ✅ | 本地提醒插件选型 | **定案：`flutter_local_notifications 22.x` + `timezone` + `flutter_timezone`**。系统级排期（`zonedSchedule`，Android 精确闹钟 / iOS 日历触发），App 被杀仍到点；`is_notified` 在「排期成功 / 补发成功」时置 1 防重复；重启后由 boot receiver 恢复排期 | 03 §3、Phase 6 |
| **Q15** ✅ | 硬删除的周期实例会不会被生成引擎重新写回？ | **实施期发现并修复**：会。幂等键 `UNIQUE(periodic_item_id, cycle_index)` 在实例被删后空出 → 新增 `periodic_skips` 墓碑表（schema v2.2），生成时跳过、撤销删除时清除 | 02 §4.4、04 §5、M1 |
| **Q7** ✅ | 状态管理方案 | **定案：Riverpod**（`flutter_riverpod`，**不引入** `riverpod_generator` / `build_runner`）。理由：① DB 读写全异步，`AsyncValue` 直接省掉每页 loading/error/data 样板；② 待办页与周期页双向依赖，`ref.invalidate` 比手写通知可靠；③ `overrideWith` 让 22 条验收用例可脱离真机数据库运行。落地约定（provider 命名、失效矩阵、全局 vs 局部状态边界）见 [07 §A.1](./07-开发计划-待办与周期.md) | 04 §2、07 §A.1、Phase 2 架构 |
| **Q8** ✅ | 修改周期 `start_date` / `interval_*` 后已生成实例如何处理 | 采纳默认：**不追溯**，已有实例保持原日期，新规则只对未生成轮次生效，`completed_count` 不重置 | 01 §4.6、02 §7.4、Phase 3 |
| **Q9** ✅ | 周期实例的删除语义 | 采纳建议：**三级删除**——删这一次（默认）/ 删该周期项的未来实例 / 删整个周期 | 02 §7.3、04 §4.3 |
| **Q10** ✅ | 待办页默认展示范围与分组 | 采纳建议：**逾期 · 今天 · 明天 · 后续 · 已完成(默认折叠)**，替代原"待处理/已完成"两组；空分组不渲染 | 01 §5.2、04 §4.1、Phase 2 |
| **Q12** ✅ | 缩短周期导致周期项 `day_offset` 越界 | 采纳建议：**阻止保存**并列出冲突项，要求用户先调整 | 02 §7.2、04 §4.2 |
| **Q13** ✅ | 取消完成是否回退 `completed_count` | 采纳建议：**回退**（不小于 0） | 02 §7.3、04 §4.2 |
| **Q14** ✅ | 周期是否提供"周 / 月"默认预设 | 提供 每天 / 每 2 天 / 每周 / 每 2 周 / 每月 / 每年 / 自定义；`interval_days` 拆为 `interval_type` + `interval_value`，MONTH/YEAR 走**日历算术**而非 30/365 天近似 | 01 §4.1、02 §4.1、Phase 3 |
| ~~**Q11**~~ | ~~子任务全完成是否自动完成父任务~~ | **已随 Q2 失效**（子任务功能移除） | — |
